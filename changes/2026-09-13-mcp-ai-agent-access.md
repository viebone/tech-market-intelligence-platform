# Change Request: Bring-your-own-AI access via a remote MCP server

## Signal
See: `research/2026-09-13-mcp-ai-agent-access.md`

## Outcome
See: `outcomes/bring-your-own-ai-agent-access.md`

## Change Type
`new-feature` — no existing surface, spec, or outcome covers external AI agents (Claude,
ChatGPT, Gemini CLI, or any MCP-compatible client) authenticating against this platform and
querying its market intelligence directly. Full chain applies.

- 2026-09-13: Triaged as `new-feature` — no existing outcome covers external-AI-agent access; new outcome `bring-your-own-ai-agent-access` created (priority: high, source: business, at user's explicit direction — cited reasons: token/cost savings vs. platform-hosted LLM, user choice of assistant, strategic/ecosystem positioning, learning value).
- 2026-09-13: Confirmed this can run in parallel with the 3 in-progress change requests (different files/layers); flagged one file-level overlap risk to re-check once the backend spec is written (`requirements-backlog-batch-catchup` also touches requirements/skills data).
- 2026-09-13: Flagged (not resolved) that `design/foundations.md`'s existing Scope carve-out only covers *operator-only* internal tooling — this feature's human-facing connections-management surface is a different shape (end-user account/settings, not operator tooling, not a Task-Panel conversation) and needs its own explicit ruling in foundations before IA is touched.
- 2026-09-13: Resolved via `design/foundations.md` v1.1 → v1.2. Grounded directly in the user's own framing: *"we provide data, we provide access to curated data, insights and stories... we don't want free access to the db, we want to give access in a controlled way... always based on user needs and outcomes."* Two changes:
  1. **Scope** — added a third carve-out category, "external access surfaces," alongside consumer-facing product and operator-only internal tooling. Split in two: the connections-management surface (exempt from the Agentic Conversational UI paradigm, like pipeline-visibility, but *not* exempt from Principle 5 — revoking a connection is itself direct manipulation); and the external tool-contract surface (no rendering surface here at all, so the presentational mechanics of every principle don't apply — but their *values* do, per the new Principle 9).
  2. **New Principle 9 — Curated Access, Never Raw** — generalizes past MCP specifically: every current and future access surface (this product's UI, an internal tool, MCP, or anything added later) is a named, curated, taxonomy-authoritative operation, never raw/free-form/direct DB access, for any consumer at any plan tier. This is the mechanism that makes "always based on user needs and outcomes" hold for every future functionality without re-litigating the question each time. Also added a matching "Curated Access Integrity" goal (Design Goals & Metrics) and an "External access" category (What this rules out).
- 2026-09-14: `/new-experience` drafted `design/mcp-access/experience.md` (`status: draft`). Split into Part 1 (Connections & Permissions — a real settings-style screen in this product's own UI, reachable via a proposed new TopBar entry point) and Part 2 (What a Good Answer Feels Like — no UI at all, since Claude/ChatGPT/Gemini render the answer themselves; specifies user-outcome intent and binding data-legibility obligations for the backend spec instead). Deliberately did not design tool names/parameters/schemas — left entirely to `/new-backend-spec`. Left five Open Questions for IA, visual-design, content, and backend to resolve (TopBar entry-point treatment, a reusable Settings Page layout pattern, scope-chip/instruction wording, plan-gated upgrade path location, and whether connections should ever expire on their own).
- 2026-09-14: `/new-information-architecture` first resolved the entry-point open question in `design/information-architecture.md` v2.5 via a new TopBar **Account** entry opening an **Account Menu**, with **Connect Your AI** as its first item.

- 2026-09-15: `/new-backend-spec` saved `backend/specs/mcp-access/api.md` (`status: draft`). Explicit **local-only, no-deploy** note per the user's instruction, carried forward for `/implement-backend`. Key decisions: (1) six MCP tools, each a thin wrapper around the *existing, already-shipped* `market_query.py` functions the in-app chat feature already trusts — no new, untested query logic on a public surface; (2) deliberately **excluded** a company-level job-demand tool (the underlying `query_market_data` has no `company` filter today) and any pre-composed "snapshot"/"compare" tool (per the outcome's explicit "data primitives, not pre-written reports" direction) — both flagged as Out of Scope, not silently invented; (3) a shared response envelope (`data` + `meta`) makes every tool response self-describing (unit, scope, time window, source, taxonomy version) inline, satisfying the experience spec's Part 2 binding contract; (4) OAuth 2.1 + PKCE + Dynamic Client Registration (RFC 7591/7636), matching MCP's own authorization spec, so any real MCP client works without a bespoke integration; (5) revocation checked live on every call (no cache, no queue) — the literal mechanism behind "immediate, no grace window"; (6) resolved both Open Questions the experience spec left open — no self-serve upgrade path (no billing system exists yet, point back to the product), and connections don't auto-expire (only short-lived access tokens do, via refresh); (7) confirmed no file-level overlap with `requirements-backlog-batch-catchup` (it touches the write/ingestion path; this spec only reads via an already-existing function) — safe to implement in parallel, as anticipated. Also corrected one experience-spec assumption: a "disconnected by the client's own side" connection state isn't observable over real OAuth and was dropped rather than faked.
- 2026-09-15: `/new-frontend-spec` saved `frontend/specs/mcp-access/architecture.md` (`status: draft`). At the user's explicit direction ("each part of my app should be clearly differentiated and documented"), led with an Architecture Overview naming exactly one integration point with existing code (`OutputPanel.tsx` gains a two-branch render, nothing else in `market-health` changes) and two new, self-contained feature areas (`account`, `mcp-access`) that don't import from each other beyond a `useSession()` hook. Caught and resolved one cross-spec ambiguity before it reached implementation: whether the OAuth consent screen is server-rendered or an SPA route — resolved as server-rendered Jinja2 on the backend (matching the existing `/admin/login` precedent in `admin_main.py`), removing an `OAuthConsentPage` component this spec had initially drafted and updating `backend/specs/mcp-access/api.md`'s `GET /mcp/oauth/authorize` to say so explicitly. Added a small clarifying cross-reference to `frontend/specs/market-health/architecture.md`'s "Authentication and user session management" out-of-scope line so it reads as a deliberate, still-true boundary rather than stale text now that a real session exists elsewhere in the codebase.
- 2026-09-15: `/implement-backend` built `backend/src/mcp_access/` (server.py, tools.py, oauth.py, envelope.py, taxonomy.py, db_helpers.py, account.py, templates/consent.html), `backend/src/auth.py` (new consumer session module), six new tables in `db.py`, two new caps in `ai_interaction_settings.py`, and mounted everything on `main.py`. **Verified against real installed dependencies, not left as untested assumptions** — installed `mcp` into the project's actual `venv_linux` and found two real integration problems before they could surprise the user:
  1. **Dependency conflict.** `mcp`'s 2.x releases require `starlette>=1.x`, incompatible with this project's `fastapi==0.115.0` pin. Resolved by pinning `mcp==1.9.4` (verified: the oldest 1.x release that both satisfies `fastapi`'s starlette constraint and actually exposes `FastMCP.streamable_http_app()`, the mount point `server.py` needs — confirmed absent in 1.x releases below 1.8.0 by direct import testing) plus a matching `sse-starlette==3.0.3` pin. `pip check` confirms a fully consistent dependency set.
  2. **A real code bug, not a dependency issue.** `mcp_access/server.py` initially opened with `from __future__ import annotations`, matching every other file in this codebase — but `mcp`'s `Tool.from_function` inspects each tool parameter's *runtime* annotation object, not a resolved string, and raised `TypeError: issubclass() arg 1 must be a class` on the first tool with any parameters once that import was active. Reproduced directly, fixed by omitting the import in that one file (documented prominently in its module docstring and in the backend spec's Tech Decisions, so a future edit doesn't reintroduce it), then re-verified.

Also fixed one real gap found during this same verification pass: the OAuth consent POST handler didn't re-validate `redirect_uri` against the registered client (only the GET render did), which would have been an open-redirect vector on tampered form input — fixed to re-validate on every POST. `backend/specs/mcp-access/api.md` updated to `status: implemented` with both findings recorded in its External Dependencies and Tech Decisions sections. **Not run against a live Postgres or a real MCP client — that's the user's own next step, locally.**
